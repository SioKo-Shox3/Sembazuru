# Sembazuru Protocol v0 (skeleton)

Status: **skeleton** — structure and invariants are fixed here; message details
and the data-plane transport are deliberately TBD until M3 measurements exist.
See `docs/DESIGN.md` §3–§4 for the architecture this serves.

## 1. Design principles

1. **Control and data are separate planes.** Scheduling decisions are rare and
   small; file supply is frequent and latency-critical. One transport cannot
   serve both well, and coupling them lets the slow path drag the fast path.
2. **The data plane is latency-driven, not throughput-driven.** A C++ compile
   issues thousands of small `stat`/`open` calls (header resolution). The
   enemy is per-operation round-trips, not bandwidth. Every data-plane design
   choice is judged by round-trips eliminated.
3. **Content addressing everywhere.** Files are referenced by digest, never by
   transferring bytes that the other side may already have (CAS, M4).
4. **The protocol assumes failure.** Every remote action must be abortable and
   locally replayable (local fallback is a hard requirement, DESIGN.md §2).
5. **Bespoke on purpose.** We borrow REAPI's CAS/action-cache *design ideas*
   but not its execution protocol; our unit of execution is a virtualized
   process with on-demand I/O, which REAPI does not model.

## 2. Roles

| Role | Plane(s) | Summary |
|---|---|---|
| **Agent** (local) | control + data | Owns the build session: schedules actions, serves the local filesystem to workers, receives outputs. |
| **Worker** (remote) | control + data | Executes hooked processes in a sandbox; requests file content on demand; returns outputs. |
| **CAS** | data (+ thin control) | Digest-addressed blob store; dedup and action cache. May be colocated with the Agent in small deployments. |

## 3. Control plane — gRPC/Protobuf

Transport: gRPC over TCP+TLS. Chosen for maturity and evolvability; its
framing overhead is acceptable here because control traffic is low-rate.

Sketches below are illustrative, not yet `.proto` source. Field numbering,
error model (rich status codes), and auth metadata are deferred to the first
implementation milestone that needs them (M3).

### 3.1 Session & registration

```proto
service Coordination {
  // Worker → Agent (or future scheduler): announce capabilities, keepalive.
  rpc Register(RegisterRequest) returns (RegisterResponse);
  rpc Heartbeat(stream HeartbeatPing) returns (stream HeartbeatPong);
}

message RegisterRequest {
  string worker_id = ...;
  Capabilities caps = ...;   // protocol_version, os_build, arch, cpu_count,
                             // memory, data_plane_transports, supports_auth
  string auth_token = 10;    // shared cluster token (M7, ADR 0006)
  // field 11 reserved: future client-cert / attestation (mTLS / zero-trust)
}
```

Capability exchange carries **protocol_version** (see §6) and the list of
data-plane transports the peer supports, so the data plane can evolve
independently of the control plane.

**Auth (M7, ADR 0006).** The trust model is **LAN-trusted**: a cluster shares
one secret (`auth_token`, distributed out-of-band via `SEMBAZURU_CLUSTER_TOKEN`).
The worker presents it on `Register`; the agent matches it and rejects a wrong/
absent token. The same token gates the data-plane session handshake (§4.1/§5).
A `supports_auth` capability flag (§6) advertises that a worker speaks the
handshake. When no token is configured the agent accepts unconditionally (the
M5/M6 LAN start). Field 11 stays reserved so a wire-compatible move to client
certs / mTLS (zero-trust) remains open.

### 3.2 Action lifecycle

An **Action** = one process execution (command line, env, working dir,
identity of the input *root* — not an input file list; inputs are discovered
on demand, which is the whole point).

```proto
service Execution {
  // Agent → Worker: run this process under virtualization.
  rpc Execute(ExecuteRequest) returns (stream ExecuteEvent);
  rpc Abort(AbortRequest) returns (AbortResponse);
}

message ExecuteRequest {
  string action_id = ...;
  Command command = ...;        // argv, env, cwd (as seen locally)
  string session_id = ...;      // binds to a data-plane file session
  Digest predicted_inputs = ...; // optional prefetch hint manifest (M5)
}

message ExecuteEvent {
  oneof event {
    StateChange state = ...;    // QUEUED → PREPARING → RUNNING →
                                // (COMPLETED | FAILED | ABORTED)
    OutputAvailable output = ...; // digest + path of a produced file
    ExitStatus exit = ...;      // exit code, timing, stats
  }
}
```

State machine (worker-side):

```
QUEUED → PREPARING → RUNNING → COMPLETED
            │            │   └→ FAILED  (worker reports cause)
            └────────────┴──→ ABORTED  (agent gave up / fallback fired)
```

**Fallback rule:** the Agent may locally re-execute an action at any moment
without worker cooperation (worker death, network partition, latency budget
exceeded). Therefore actions must be side-effect-free outside their declared
output set, and output publication must be atomic (no torn outputs visible to
the build system).

### 3.3 Open control-plane questions

- Worker discovery (static list first; mDNS/registry later, M5).
- Trust model: **decided — LAN-trusted** (M7, ADR 0006). `Register` carries a
  shared `auth_token`; client-cert/attestation (mTLS, zero-trust) stays a
  wire-compatible future via reserved field 11.
- Scheduling is Agent-side in v0 (no central scheduler before M5).

## 4. Data plane — file supply (transport TBD)

The data plane serves one purpose: make the worker-side hooked process see the
Agent-side filesystem with the fewest possible round-trips. The **transport is
deliberately not chosen here** — candidates and the selection criterion are
fixed instead (see §4.4).

### 4.1 Operation semantics (transport-independent)

All operations are defined request/response over an ordered, reliable,
multiplexed byte stream abstraction. Everything is designed batch-first:
the singular forms are just batches of one.

| Op | Semantics | Latency note |
|---|---|---|
| `StatBatch(paths[]) → meta[]` | Existence + attributes + digest for many paths in one round-trip. | Header resolution probes many non-existent paths; negative results MUST be batchable and cacheable. |
| `OpenRead(path) → (digest, size, first_chunk?)` | Open-for-read resolves to content identity; the first chunk MAY be inlined to make `open`+first-`read` one round-trip. | |
| `Read(digest, offset, len) → bytes` | Content fetch by digest (CAS-mediated; worker-local cache consulted first, M4). | |
| `DirList(path, depth) → entries[]` | Bulk directory snapshot, prefetching metadata for likely subsequent stats. | |
| `WriteBack(path, digest, bytes/chunks)` | Worker → Agent output return. Streamed, atomic publish on close. | |
| `PrefetchHint(manifest)` | Agent-pushed: "you will likely need these"; worker warms cache ahead of process I/O. | The M5 dependency-prediction hook. |

Invariants:

- **Snapshot consistency per session:** a file session observes the local
  filesystem as of session start (digest-pinned); mid-build local edits do not
  tear a running action.
- **Digests are the cache key end-to-end** (CAS, worker cache, action cache).
  Algorithm choice is open (DESIGN.md §9) — candidate BLAKE3, decided with CAS
  chunking strategy in M4.

### 4.2 Wire format

Length-prefixed binary frames, fixed small header (op, request id, flags),
payloads defined per-op. Request ids allow out-of-order completion over a
single connection. **No protobuf on the hot path** unless measurement shows
its cost is negligible (M3 decides).

### 4.3 CAS transfer

Chunked upload/download keyed by digest; `Has(digests[])` batch-probe before
upload. Chunking strategy (fixed vs content-defined) decided in M4 with real
data.

### 4.4 Transport candidates & selection criterion (M3 decides)

| Candidate | For | Against |
|---|---|---|
| TCP + custom framing (baseline) | simplest, debuggable, no new deps | head-of-line blocking across multiplexed requests |
| QUIC (e.g. quinn) | stream multiplexing without HOL blocking, connection migration | userspace UDP cost on Windows, more moving parts |
| gRPC streams (strawman) | one stack for everything | framing/HPACK overhead on tiny ops — expected to lose; kept only as a measured baseline |

**Selection criterion (fixed now):** measured wall-clock of a representative
`cl.exe` compile (per DESIGN.md M3 "Done when": not significantly worse than
local), on a LAN with ~0.5–1 ms RTT, with cold worker cache. The transport
that wins that benchmark — not the one with the nicest architecture — ships.

## 5. Security (M7 — trust model & auth: ADR 0006)

Trust model: **LAN-trusted** (ADR 0006). Authentication is a **shared cluster
token** distributed out-of-band (`SEMBAZURU_CLUSTER_TOKEN`); zero-trust / mTLS is
a deferred, wire-compatible future (reserved field 11 + capability flag).

- **Control plane (auth — landed):** the worker presents `auth_token` on
  `Register`; the agent matches it and rejects a wrong/absent token (closing the
  unauthenticated-`Register` injection path). No token configured ⇒ accept
  unconditionally (M5/M6 LAN start).
- **Data plane (auth + path scoping — landed):** the worker's first frame is
  always a `Hello` (op 7, M7.1) that opens the session — it carries the shared
  token (M7.0, may be empty when auth is off) and DECLARES the session's input
  root (M7.1). The agent validates the token (closing the unauthenticated
  file-supply path) and then **scopes all read ops to that declared root**:
  StatBatch/OpenRead/DirList outside the root report non-existence, so a rogue or
  buggy worker cannot read arbitrary agent-side files (e.g. `~/.ssh/id_rsa`) — the
  arbitrary-absolute-path supply of M3–M6 is gone. An empty root means unscoped
  (legacy/tests). The hook↔worker VFS named pipe is a local, in-machine path and
  is **not** token-gated; the trust boundary is the worker→agent TCP.
- **Output write-back (declared-output scoping — deferred):** a worker's
  `WriteBack` publishes to an agent-side path; bounding it to the action's
  declared output set (§3.2) is deferred with 2-machine write-back. Today the
  single-machine model writes outputs to the local path the command names (no
  write-back), and content-addressing + digest verification + atomic publish make
  a torn or wrong-byte output structurally impossible.
- **Encryption (TLS — deferred):** required only when traffic leaves the
  localhost/LAN-trusted scope. On a trusted LAN it is **off by default**; the
  token provides authentication, not confidentiality. Real TLS wiring (tonic
  `ServerTlsConfig`/`ClientTlsConfig` on the control plane; `tokio-rustls` on the
  data plane) rides the same deferral as the real-2-machine-LAN measurement
  (ADR 0002/0004) and the zero-trust decision — there is no production condition
  to validate the encrypted path against until then.
- **Integrity (always on):** digest verification on every CAS object regardless
  of TLS (integrity is free; ADR 0003 BLAKE3). Workers treat all supplied content
  as untrusted input; agents treat worker outputs as untrusted until
  digest-verified.

## 6. Versioning

- Single `protocol_version` integer negotiated at Register time; v0 = 0.
- v0 makes **no compatibility promises** — wire breaks are allowed until M3
  ships, then the data plane freezes per minor version.
- Capability flags (not version sniffing) gate optional features
  (e.g. `PrefetchHint`).

## 7. Open questions (tracked, not blocking the skeleton)

Linked from DESIGN.md §9:

1. Data-plane transport — §4.4, measured in M3.
2. CAS hash + chunking — M4.
3. Trust model (LAN vs zero-trust) — **decided: LAN-trusted, shared token**
   (M7, ADR 0006). Zero-trust/mTLS stays a wire-compatible future (§3.1/§5).
4. Fallback thresholds (how long to wait before local re-exec) — M3 tuning.
5. How the VFS approach decision (`docs/decisions/0001-vfs-approach.md`)
   changes §4.1: a filter-driver or ProjFS-based worker VFS consumes the same
   op set, but hook-based virtualization may need extra ops (e.g. handle
   table sync for child processes). Revisit after that decision lands.
