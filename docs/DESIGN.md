# Sembazuru — プロジェクト設計概要 (rev.2)

> 千羽のワーカーが一羽の鶴のように、一つのビルドを折り上げる。

任意の Windows プロセスを **無設定で分散実行する** オープンソース基盤。
Incredibuild の本当の堀である「プロセス仮想化」を OSS で再現し、既得権益に胡座をかいた価格体系を過去のものにすることを目的とする。

> **rev.2 の変更点:** VFS 実装方式の決定を M0 に格上げ／M3 に初回レイテンシ対策を内包／M5 の完了条件を現実化／ライセンス情報を一次ソースで裏取りして反映／競合分析セクションを追加。

---

## 1. ビジョンと立ち位置

ほとんどの「分散ビルド」OSS（FASTBuild など）は、専用のビルド記述や限定的なコンパイラ対応に縛られており、性能・汎用性ともに有料製品に届かない。Sembazuru が狙うのはそこではない。

狙うのは **「すでに存在する任意のビルドを、ビルドシステムに手を入れずにそのまま千の分身に分けて走らせる」** 体験そのもの。これが Incredibuild が高値で売れている唯一の理由であり、ここを無料で提供できれば価格優位は消滅する。

### コアの賭け

技術的中核は分散コンパイルではなく **プロセス仮想化** である:

- ローカルで起動された `cl.exe` 等のプロセスの全 I/O（ファイル・子プロセス・レジストリ）を API フックで横取りする
- そのプロセスをリモートワーカー上で起動し、ローカル環境をリモートに「見せかける」
- 入力ファイルは事前一括転送ではなく **オンデマンドでストリーミング** する（ここが速度の肝であり、最大の難所でもある）
- 出力はローカルへ返送し、呼び出し側からは「ローカルで普通に走った」ように見せる

これが成立すれば、コンパイラの種類もビルドシステムの種類も原理的に問わなくなる。

## 2. 設計原則

- **無設定で動くことが最優先** — 設定ファイルを書かせた時点で Incredibuild に負けている
- **既存ビルドへの非侵襲** — ユーザーのビルドスクリプトを書き換えさせない
- **ローカルフォールバック必須** — ネットワークやワーカーが落ちても、最悪ローカルで完走する。壊れないことが信頼の土台
- **各フェーズが単体で公開価値を持つ** — 完成まで何年かかっても、途中の成果物が独立して有用であること
- **決定性を疑い続ける** — 「同じ入力なら同じ出力」が崩れた瞬間、分散ビルドは静かに壊れる。正確性は速度より上位
- **巨人の肩に乗る領域を見極める** — MIT で取り込める基盤（フック等）は遠慮なく使い、エネルギーは差別化領域（独自プロトコル・汎用化）に集中する

### 非ゴール（少なくとも当面）

- 収益化・商用サポート
- Linux/macOS ファースト（Windows と MSVC エコシステムが主戦場。Linux は後追いで十分）
- REAPI 実行プロトコル互換（CAS の設計思想だけ借り、実行プロトコルは独自にする方針は確定済み）

## 3. アーキテクチャ全体像

```
┌─────────────── ローカルマシン ───────────────┐
│                                              │
│  ビルドシステム (MSBuild/Ninja/UBT)          │
│        │ プロセス起動を横取り                │
│        ▼                                     │
│  ┌──────────────┐   フック層 (C++ / Detours) │
│  │ Interceptor   │  ファイルI/O・子プロセスを  │
│  │  (注入DLL)    │  捕捉                       │
│  └──────┬───────┘                            │
│         │                                    │
│  ┌──────▼───────┐                            │
│  │  Local Agent  │ (Rust)                     │
│  │  - VFS        │ オンデマンドでファイル供給  │
│  │  - スケジューラ│ どのワーカーに割るか        │
│  │  - プリフェッチ│ 初回レイテンシを潰す        │
│  │  - フォールバック                          │
│  └──────┬───────┘                            │
└─────────┼────────────────────────────────────┘
          │ 独自プロトコル
          │  制御プレーン (gRPC) / データプレーン (別途)
          ▼
┌──────── Worker群 ────────┐   ┌──── CAS ────┐
│  Worker (Rust)            │   │ ハッシュ重複 │
│  - サンドボックス内で      │◄──┤ 排除ストア   │
│    プロセス実行           │   │ アクション   │
│  - ローカルキャッシュ      │   │ キャッシュ   │
└──────────────────────────┘   └─────────────┘
```

### 主要コンポーネント

| コンポーネント | 役割 | 想定言語 |
|---|---|---|
| **Interceptor** | プロセスに注入され I/O・子プロセスをフック | C++ (Detours ベース) |
| **Local Agent** | フック結果を受け、VFS・スケジューリング・プリフェッチ・フォールバックを担う司令塔 | Rust |
| **Worker** | リモートでプロセスをサンドボックス実行 | Rust |
| **CAS** | コンテンツアドレス可能ストレージ。重複排除とキャッシュ | Rust |
| **Protocol** | Agent ⇔ Worker ⇔ CAS の独自通信仕様。制御とデータを分離 | Protobuf/gRPC + データ転送用トランスポート |

## 4. 技術スタックの推奨

- **フック層は C++ + Detours（MIT）に乗る** — 自前でゼロから API フックを書くのは車輪の再発明であり保守地獄。Detours は枯れているが**安定版が 2018 年で更新停止**しているため、フォークを自分で保守する前提で採用する。ここだけ薄く C++、それ以外は Rust に寄せる
- **Agent/Worker/CAS は Rust** — メモリ安全性、並行処理、配布バイナリの扱いやすさで有利。インフラソフトの長期保守に向く
- **プロトコルは制御とデータを分離する** — スケジューリング等の制御プレーンは gRPC で開始。**VFS の大量小ファイル供給（データプレーン）は gRPC のフレーミングオーバーヘッドが効くため、早期に別トランスポート（QUIC や独自軽量プロトコル）を計測・検討**する。ここを一本化すると「無料相応」の速度に沈む
- **ライセンスは Apache-2.0** — 特許条項があり企業採用の障壁が低い

## 5. 先行資産とライセンス（一次ソース裏取り済み）

車輪の再発明を避けるため、着手前に以下を読み込む。**ライセンス区分が「取り込み可」か「学習のみ」かを厳密に分ける。**

| 資産 | ライセンス | 扱い |
|---|---|---|
| **Detours** | MIT（安定版 4.0.1 は 2018 年で更新停止） | **取り込み可。** フック層の土台。フォーク保守前提 |
| **BuildXL** | コア MIT（一部 MS 内部 NuGet は非公開） | **MIT 部分は取り込み可。** サンドボックス設計の教材として最良 |
| **UBA (Unreal Build Accelerator)** | **Unreal Engine EULA**（MIT/Apache ではない） | **学習のみ。コード非取り込み。** Epic アカウント紐付けが必要。clean room 維持のため仕様観察に留める |
| **REAPI (Remote Execution API)** | Apache-2.0 | CAS／アクションキャッシュの設計を流用。実行プロトコルは借りない |
| **Goma / Reclient** | OSS | スケジューリングとキャッシュの実運用知見 |

> **重要:** UBA は最も近い「敵」の設計だが、ライセンス上コードを自分のリポジトリへ持ち込むと危険。設計思想を読んで理解するに留め、実装は自分で起こすこと。取り込み前に各 LICENSE ファイル原本を必ず確認する（特に UE EULA は独特）。

## 6. 競合・先行事例の分析

着手前に下記を実地調査し、「既に埋まっている隙間」と「空白地帯」を切り分ける。

- **Incredibuild** — 倒すべき相手。本当の堀は技術そのものより、MSVC のエッジケースに対する十数年分の互換性蓄積。ここは設計では消せず時間でしか埋まらない
- **UBA + Horde** — Epic 純正・無料。UE 市場という最大の収益源を Epic 自身が侵食中。ただし UE エコシステムに密結合で、汎用ツールではない
- **XiaoBuild** — UBA ベースの MIT プロジェクトで Incredibuild 相当を無料提供。**最も近い既存 OSS 競合**。何ができていて何が未対応かを必ず確認する
- **FASTBuild** — 専用ビルド記述が必要で汎用性に欠ける。性能も無料相応で頭打ち
- **sccache-dist / Bazel RBE 系** — Linux 中心で Windows/MSVC が弱い。ここが Sembazuru の狙う空白

### Sembazuru の差別化軸

「UE 専用ではない」「専用ビルド記述が不要」「Windows/MSVC ファースト」「最終的にコンパイル以外も分散（M8）」。この 4 点が同時に成り立つ OSS は現状存在しない。ここが勝ち筋。

## 7. マイルストーン

期限は設けない。各マイルストーンは **「完了条件（Done when）」を満たした時点で次へ進む** 方式とする。M1・M2 は単体 OSS として先に公開してフィードバックを得るのが望ましい。

### M0 — 偵察と土台づくり（重要な意思決定を全部ここで固める）

- BuildXL のサンドボックス実装を読み、フック手法を理解する
- Detours を採用し、フォーク保守方針を決める
- **【格上げ】VFS の実装方式を決定する** — ユーザーモード VFS か、ファイルシステムフィルタドライバか。後者はカーネル署名（EV/WHQL）が必要で難度・配布要件が激変するため、**この一択を M0 で決着させる**（プロジェクト全体の難度を左右する前提条件）
- 独自プロトコルの仕様骨子（v0）を文書化。制御／データプレーン分離を明記
- XiaoBuild 等の競合を実地調査
- リポジトリ構成・ライセンス（Apache-2.0）・CI（GitHub Actions Windows ランナー）を整備
- **Done when:** 注入 DLL で `cl.exe` の `CreateFile` を 1 つフックしログを出せる最小 PoC が動き、VFS 方式とプロトコル骨子が文書として確定している

### M1 — プロセス記録器（The Tracer）

フックを「観測」に徹して完成させる。これ単体で「ビルド依存トレーサー」として公開価値がある。

- ファイル I/O（読み/書き/存在確認）、子プロセス生成、レジストリ、環境変数を全捕捉
- トレース結果を構造化フォーマット（バイナリ + JSON エクスポート）で出力
- `cl.exe` / `link.exe` / `clang-cl` で検証
- **Done when:** 任意のコンパイラ呼び出しについて、入力ファイル集合と出力ファイル集合を含む完全な依存グラフを、再現性をもって取得できる

### M2 — 決定性ハーネス（Determinism Harness）

分散の前に「同じ入力なら同じ出力」を保証する仕組みを作る。ここを飛ばすと後で静かに壊れる。

- 同一入力でビルドを 2 回回し、出力バイト列を比較する自動ハーネス
- 非決定性の発生源（タイムスタンプ、`__DATE__`/`__TIME__`、絶対パス埋め込み、PDB）を特定し正規化ルールを定義
- 入力ハッシュ → 出力ハッシュのマッピングを記録
- **Done when:** 代表的な C++ 翻訳単位群で、入力ハッシュから出力ハッシュが安定して再現する

### M3 — 単一リモート実行（1:1 Remote Execution）

技術的中核の証明。**ここで「動く」だけでなく「実用速度で動く」までを完了条件に含める**（rev.1 の最大の甘さを是正）。

- フック済みプロセスをリモートワーカー上で起動
- ファイル読み取りを **オンデマンドでネットワーク越しに供給** する VFS を実装
- **【内包】初回レイテンシ対策を最初から設計に織り込む** — C++ コンパイルはヘッダ解決で大量の小ファイル `stat`/`open` を撃つ。1 回ずつ往復させると「動くが遅い」状態に陥る。バッチ化・先読み・往復削減を M3 の設計要件とする
- 書き込みをローカルへ返送
- 失敗時はローカル実行へフォールバック
- **Done when:** 1 台のワーカーで `cl.exe` を完全リモート実行し、ローカル実行と **バイト一致** の `.obj` が得られ、かつ **その実行時間がローカル実行から大きく劣化していない**（往復レイテンシで破綻していない）

### M4 — CAS とキャッシュ

転送とコンパイルの重複をゼロに近づける。

- ハッシュベースのコンテンツアドレス可能ストレージで重複排除
- ワーカー側のローカルキャッシュ（一度見たヘッダ/SDK ファイルは再送しない）
- アクションキャッシュ（入力ハッシュ → 出力。同一コンパイルはスキップ）
- **Done when:** 同一プロジェクトの 2 回目のビルドで、ファイル転送量とコンパイル実行がほぼゼロになる

### M5 — スケジューラと多ワーカー（Scheduler & Fanout）

「分身が千になる」フェーズ。性能で有料製品を超えにいく。

- 複数ワーカーへのタスク分配
- ワーカー発見・ヘルスチェック・切断時の再割り当て
- 依存予測プリフェッチ（過去ビルドの依存情報で初回往復を事前に潰す）
- **Done when:** **コンパイルフェーズについて** ワーカー数に対し実用的な並列効率（目安 8 割以上）でスケールする。※リンク（`link.exe`）やプリプロセスは分散不可能な直列ボトルネックとして残るため、「全体が線形」は完了条件にしない（rev.1 の非現実的な目標を是正）

### M6 — ビルドシステム統合（Integrations）

一般ユーザーが「無設定で」使える状態にする。

- MSBuild / Visual Studio（プロセス起動の横取り口を提供）
- CMake / Ninja
- Unreal Engine（UnrealBuildTool フック）— Incredibuild の最大収益源を直接奪う
- **Done when:** 既存プロジェクトを最小限の設定で分散ビルドできる

### M7 — 堅牢化と運用（Hardening）

「壊れない」を作る。OSS インフラが信頼されるかの分水嶺。

- EDR/AV 対策 — API フックがマルウェア誤検知されないよう、バイナリ署名と主要ベンダーへのホワイトリスト申請
- Windows Update 追従の CI マトリクス（複数 Windows ビルドで自動回帰。Detours フォークの追従もここ）
- ワーカー間認証・サンドボックス強化（信頼できないコードを走らせる前提の防御）
- 障害時フォールバックの網羅
- **Done when:** 実プロジェクトで日常的に使い続けられる信頼性に到達

### M8 — 汎用化（Beyond Compilation）— 本丸

ここが「Incredibuild 倒産」の核心。コンパイル以外を取り込む。

- シェーダーコンパイル、テスト実行、アセット処理など任意プロセスの無設定分散
- コンパイラ非依存・ビルドシステム非依存の「汎用プロセス分散レイヤー」として確立
- **Done when:** コンパイル以外のワークロードが、専用対応なしにそのまま分散される

## 8. 横断的な懸念（全フェーズで意識する）

- **MSVC リモート実行のライセンス問題** — `cl.exe` をリモートに配布・実行するのは Visual Studio ライセンス上グレー。技術では解けないため、**clang-cl 対応を常に並走させ逃げ道を確保**する。ゲームスタジオは MSVC ロックインが多いため、clang-cl だけでは完全代替にならない点も織り込む
- **UBA のライセンス汚染** — 設計学習に留め、コードを取り込まない。clean room を保つ
- **EDR/AV による誤検知** — API フックはマルウェアの常套手段でもある。署名と申請を後回しにすると採用が止まる
- **Windows 内部仕様 / Detours の追従** — フックは OS アップデートで壊れうる。Detours 上流が止まっているため、フォークの保守責任は自分にある。CI で継続検知する
- **正確性 > 速度** — キャッシュ汚染や非決定性は「たまに壊れるビルド」を生み、信頼を一発で失う

---

## 9. 早期に決めるべき未解決の論点

- データプレーンのトランスポート選定（QUIC か独自軽量プロトコルか。M3 のレイテンシ計測と連動）
- CAS のハッシュ方式とチャンク戦略
- ワーカーの信頼モデル（社内 LAN 前提か、ゼロトラスト前提か）
- フォールバック判定の閾値（どれだけ待ったらローカルに切り替えるか）

> ※ rev.1 で論点だった「VFS をユーザーモードかドライバか」は M0 のタスクへ格上げ済み（前提条件のため先送り不可）。

---

## 10. 戦略的現実（折れないために）

Incredibuild の本当の堀は技術というより **MSVC のエッジケースに対する十数年分の互換性蓄積** であり、これは設計で消せず時間でしか埋まらない。したがって現実的な勝ち筋は「倒産」そのものではなく、**価格を引きずり下ろす／特定セグメント（非 UE・汎用 Windows ビルド）で確実な代替になる** こと。この現実を前提に置くほうが、長期戦で心が折れにくい。

---

## 11. 最初の一歩

**M0 → M1 の「プロセス記録器」をまず完成させ、単体 OSS として公開する。**

理由: フックという最難関要素を「観測のみ」の安全な範囲で習得でき、かつ依存トレーサーとして即座にコミュニティ価値を持つ。ここで人を集められれば、その後の長い道のりを一人で背負わずに済む。

> 一羽ずつ折る。千羽そろえば、鶴は飛ぶ。
